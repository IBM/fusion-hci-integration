    Kustomize Overlays Guide¶

    This document explains the Kustomize structure in main-cluster/configuration/, which holds the main-cluster MachineConfigPool and MachineConfig resources for the two deployment variants.

    Manual path behind the scripted setup

    The overlays are what Setup Guide step C.4 – Apply MachineConfigs applies. The values inside the direct overlay are not written by hand: generate-setup renders the two route MachineConfigs from your integration-setup.yaml. The same resources are also created by the hci-consumer operator if they are absent (see Main Cluster Configuration).

    Overview¶

    The integration uses Kustomize to manage configuration variants:

    • Base — common configuration for all deployments
    • Overlays — variant-specific additions
      • mediated — mediated topology (private network, bastion routes traffic)
      • direct — direct topology (main-cluster nodes route to the HCI gateway themselves)

    The overlay you apply follows consumer.networking.topology in integration-setup.yaml.

    Why Kustomize?¶

    • DRY — common configuration is not repeated
    • Variant management — one overlay per deployment type
    • Native to OpenShift — oc apply -k, no extra tooling
    • Version-control friendly — clear separation of base and variant

    Directory Structure¶

    main-cluster/configuration/
├── base/
│   ├── kustomization.yaml
│   ├── machineconfig-pool-hci-vm.yaml
│   └── machineconfig-hci-vm-kargs.yaml
└── overlays/
    ├── mediated/
    │   ├── kustomization.yaml
    │   └── README.md
    └── direct/
        ├── kustomization.yaml
        ├── 99-master-s390x-hci-network-route.yaml   # generated by generate-setup
        ├── 99-worker-s390x-hci-network-route.yaml   # generated by generate-setup
        └── README.md

    What generate-setup Writes¶

    File Written when Source values in integration-setup.yaml
    overlays/direct/99-master-s390x-hci-network-route.yaml consumer.networking.topology: direct provider.networking.internalSubnet, provider.gateway.ip
    overlays/direct/99-worker-s390x-hci-network-route.yaml consumer.networking.topology: direct provider.networking.internalSubnet, provider.gateway.ip

    With topology: mediated (the value in the example file) nothing is written — the mediated overlay needs no per-installation values. The base files and both kustomization.yaml files are static and are never touched by generate-setup.

    Do not edit the generated route files

    They are overwritten on every generate-setup run. To change the route, change provider.gateway.ip or provider.networking.internalSubnet and re-run generate-setup.

    Base Configuration¶

    kustomization.yaml¶

    Location: main-cluster/configuration/base/kustomization.yaml

    apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - machineconfig-pool-hci-vm.yaml
  - machineconfig-hci-vm-kargs.yaml

commonLabels:
  hci-integration: "true"
    • resources — the base manifests
    • commonLabels — hci-integration: "true" is added to every base resource

    Base Resources¶

    1. MachineConfigPool¶

    File: machineconfig-pool-hci-vm.yaml

    Purpose: a separate pool for the HCI worker VMs

    apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: hci-vm
  labels:
    machineconfiguration.openshift.io/role: hci-vm
spec:
  machineConfigSelector:
    matchExpressions:
      - key: machineconfiguration.openshift.io/role
        operator: In
        values: [worker, hci-vm]
      # Exclude s390x platform-specific MachineConfigs (multipath storage)
      - key: node-platform
        operator: NotIn
        values: [s390x]
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/hci-vm: ""
  paused: false
  maxUnavailable: 1

    Why in the base: required for every variant and has no variant-specific values. The pool name matches consumer.machineConfigPool (default hci-vm). The node-platform NotIn s390x rule keeps the s390x route MachineConfig (below) from being rendered into the x86 pool.

    2. Kernel Arguments¶

    File: machineconfig-hci-vm-kargs.yaml

    Purpose: boot settings for the x86 worker VMs

    apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-hci-vm-kargs
  labels:
    machineconfiguration.openshift.io/role: hci-vm
    node-platform: hci-vm
spec:
  kernelArguments:
    - "root=/dev/disk/by-label/root"
    - "rd.multipath=0"      # no s390x multipath storage on VMs
    - "rd.neednet=1"
    - "ip=enp1s0:off"       # disable the HCI pod-network interface
    - "ip=enp2s0:dhcp"      # cluster network interface (static DHCP lease)
  config:
    ignition:
      version: 3.5.0

    Why in the base: every worker VM needs these arguments, independent of the topology. Node role labeling is not done here — the node-labeler sidecar in the hci-consumer-operator pod labels the nodes.

    Mediated Overlay¶

    kustomization.yaml¶

    Location: main-cluster/configuration/overlays/mediated/kustomization.yaml

    apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: openshift-machine-config-operator

bases:
  - ../../base

    Characteristics: minimal — only references the base. The bastion routes the traffic to the HCI worker subnet (see Setup Guide C.2).

    When to Use¶

    Use the mediated overlay when:

    • ✅ Main-cluster nodes are on a private network (example: 10.0.0.0/24)
    • ✅ The bastion (example: 172.16.0.1) routes all traffic to the HCI gateway
    • ✅ Common in z/VM and LPAR environments

    What It Provides¶

    • The hci-vm MachineConfigPool
    • Kernel arguments for the worker VMs (including disabling enp1s0)
    • No additional routing configuration

    Application¶

    oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/mediated/

# Verify
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-hci-vm-kargs

    Direct Overlay¶

    kustomization.yaml¶

    Location: main-cluster/configuration/overlays/direct/kustomization.yaml

    apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: openshift-machine-config-operator

bases:
  - ../../base

resources:
  - 99-master-s390x-hci-network-route.yaml
  - 99-worker-s390x-hci-network-route.yaml

    Characteristics: extends the base with two routing MachineConfigs — one for the masters, one for the s390x workers.

    When to Use¶

    Use the direct overlay when:

    • ✅ Main-cluster nodes can reach the gateway's external IP (example: 172.16.1.100) directly
    • ✅ No bastion routing is wanted
    • ✅ Common in KVM and bare-metal environments

    Additional Resources¶

    Both files are rendered by generate-setup. The examples below show the output for internalSubnet: 192.168.100.0/24 and gateway.ip: 172.16.1.100.

    1. Master Node Route¶

    File: 99-master-s390x-hci-network-route.yaml

    Purpose: let the masters reach the HCI worker VMs (CSR handling, node status, scheduling, health checks)

    apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  labels:
    machineconfiguration.openshift.io/role: master
  name: 99-master-s390x-hci-network-route
spec:
  config:
    ignition:
      version: 3.5.0
    systemd:
      units:
        - name: hci-network-route.service
          enabled: true
          contents: |
            [Unit]
            Description=Add static route to HCI worker network
            After=network-online.target ovs-configuration.service
            Wants=network-online.target
            Requires=ovs-configuration.service

            [Service]
            Type=oneshot
            RemainAfterExit=yes
            ExecStartPre=/bin/bash -c 'until ip link show br-ex; do sleep 1; done'
            ExecStart=/bin/bash -c '/usr/sbin/ip route add 192.168.100.0/24 via 172.16.1.100 dev br-ex || true'

            [Install]
            WantedBy=multi-user.target

    The master unit waits for ovs-configuration.service and the br-ex bridge, because the route is bound to br-ex.

    2. S390x Worker Route¶

    File: 99-worker-s390x-hci-network-route.yaml

    Purpose: let the dedicated s390x workers reach the HCI worker VMs (pod-to-pod traffic, service endpoints, multi-architecture applications)

    apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
    node-platform: s390x
  name: 99-worker-s390x-hci-network-route
spec:
  config:
    ignition:
      version: 3.5.0
    systemd:
      units:
        - name: hci-network-route.service
          enabled: true
          contents: |
            [Unit]
            Description=Add static route to HCI worker network
            After=network-online.target
            Wants=network-online.target

            [Service]
            Type=oneshot
            RemainAfterExit=yes
            ExecStart=/bin/bash -c '/usr/sbin/ip route add 192.168.100.0/24 via 172.16.1.100 || true'

            [Install]
            WantedBy=multi-user.target

    The worker route has no dev br-ex. The node-platform: s390x label is what keeps this MachineConfig out of the x86 hci-vm pool (see the pool's NotIn rule above).

    Note: the worker route only applies to dedicated s390x workers. Compact clusters (master+worker roles) only need the master route.

    Application¶

    oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/direct/

# Base resources
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-hci-vm-kargs

# Routing MachineConfigs
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-master-s390x-hci-network-route
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-worker-s390x-hci-network-route

# Master and worker pools roll out the route (10–30 minutes)
watch oc --context ${MAIN_CLUSTER_CONTEXT} get mcp master worker
# Wait for UPDATED=True, UPDATING=False

    Creating Custom Overlays¶

    Custom overlays are not part of the supported flow, but the structure allows them. Keep them outside the generated files so generate-setup does not overwrite your work.

    Use Case: Additional MachineConfig¶

    1. Create the overlay directory: 

      mkdir -p main-cluster/configuration/overlays/custom

    2. Create kustomization.yaml: 

      apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - ../mediated          # or ../direct
  - custom-config.yaml

patches:
  - path: patch-kargs.yaml

    3. Add the custom resource: 

      # custom-config.yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  labels:
    machineconfiguration.openshift.io/role: hci-vm
  name: 99-hci-vm-custom
spec:
  config:
    ignition:
      version: 3.5.0
    storage:
      files:
        - path: /etc/custom.conf
          contents:
            inline: |
              # Custom configuration

    4. Apply: 

      oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/custom/

    Use Case: Patching the Base¶

    Example: add a kernel argument without changing the base files

    # patch-kargs.yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-hci-vm-kargs
spec:
  kernelArguments:
    - "root=/dev/disk/by-label/root"
    - "rd.multipath=0"
    - "rd.neednet=1"
    - "ip=enp1s0:off"
    - "ip=enp2s0:dhcp"
    - "custom.arg=value"     # added

    A strategic-merge patch replaces the kernelArguments list, so repeat the existing entries and append yours.

    Best Practices¶

    Overlay Design¶

    1. Keep the base minimal — only truly common configuration
    2. Use overlays for variants — do not modify the base for specific cases
    3. Do not hand-edit generated files — change integration-setup.yaml instead
    4. Test each overlay independently

    Configuration Management¶

    1. Version control — keep custom overlays in Git
    2. Tag releases — tag stable overlay versions
    3. Document changes — maintain a changelog

    Naming Conventions¶

    1. Descriptive names — mediated, direct, not variant1
    2. 99- prefix for high-priority MachineConfigs
    3. Clear labels — use labels to identify resources

    Testing¶

    1. Dry run first — oc apply -k <dir> --dry-run=client
    2. Test in dev — verify the overlay in a development cluster
    3. Validate output — oc kustomize <dir>
    4. Monitor — watch MachineConfigPool status

    Troubleshooting¶

    Kustomize Build Fails¶

    Symptoms: 

    Error: accumulating resources: accumulation err='accumulating resources from '../../base': ...

    Check: 

    # Render the overlay
oc kustomize main-cluster/configuration/overlays/direct/

# Verify the base path and referenced files exist
ls -la main-cluster/configuration/base/
ls -la main-cluster/configuration/overlays/direct/

    For the direct overlay, no such file ... 99-master-s390x-hci-network-route.yaml means the route files were not generated — check that topology: direct is set in integration-setup.yaml and re-run generate-setup.

    Resources Not Applied¶

    Symptoms: oc apply -k succeeds but resources are missing.

    # Preview what would be applied
oc apply -k main-cluster/configuration/overlays/direct/ --dry-run=client -o yaml

# Look for the resources
oc --context ${MAIN_CLUSTER_CONTEXT} get mc | grep hci

    Patches Not Working¶

    Symptoms: a patch is defined but not applied.

    # Build and inspect the output
oc kustomize main-cluster/configuration/overlays/custom/ | grep -A 20 "kind: MachineConfig"

# Verify the patch target (name and kind) matches the base resource

    Wrong Overlay Applied¶

    Symptoms: the wrong variant was applied.

    # Delete the resources of the wrong overlay
oc --context ${MAIN_CLUSTER_CONTEXT} delete -k main-cluster/configuration/overlays/<wrong-variant>/

# Apply the correct overlay
oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/<correct-variant>/

# Verify
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm
oc --context ${MAIN_CLUSTER_CONTEXT} get mc -l hci-integration=true

    Deleting an overlay also deletes the base hci-vm pool and kernel-argument MachineConfig (they are part of both overlays). Re-applying the correct overlay recreates them; no workers should be running while you do this.
