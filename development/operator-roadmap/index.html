    Operator Roadmap¶

    This document describes the vision and implementation plan for the Kubernetes Operator that manages the Fusion HCI multi-architecture integration. For the three-actor model see provider-consumer-model.md.

    Current State¶

    Implementation: Ansible Operator (operator-sdk Ansible plugin)
    Language: Ansible (roles, tasks) + Jinja2
    Operator directories: operator/hci-consumer/, operator/hci-provisioner/

    Vision¶

    Goal: Fully automated, declarative lifecycle management of multi-architecture worker nodes.

    An operator administrator applies one WorkerPool CR; the system: 1. Provisions UDN, gateway VM, and ignition via the hci-provisioner operator (Bootstrap) 2. Continuously reconciles workers.count → VMs on HCI and nodes on the LO cluster (Steady-state) 3. Handles scale-up and scale-down safely, with drain timing controlled by LOOps 4. Tears down all infrastructure cleanly on CR deletion

    HCI-side provisioning (namespace, network, quota, ticket generation) will be automated by the HCI Provider Operator (Epic 3, future work).

    Target Users: Platform administrators, SREs, DevOps teams
    Key Principles: Declarative, self-healing, observable, privilege-minimal

    Framework and Technology Choices¶

    Operator Framework¶

    Choice: Ansible Operator (operator-sdk Ansible plugin)

    Rationale: - Most of the existing integration work already uses Ansible and kubernetes.core modules - Ansible roles map directly to the observe/diff/act reconcile structure - Low barrier to contribution from the existing team - Excellent kubernetes.core.k8s and k8s_info modules for both clusters - No Go cross-compilation concern for s390x (runs on bastion natively)

    ansible-operator binary: standalone download removed in operator-sdk v1.38+. Development uses ansible-runner directly on the cluster bastion.

    Note: For performance tuning recommendations and the planned roadmap to migrate to native Golang operators, see Operator Optimization and Go Migration Guide.

    Cross-Cluster Communication¶

    Choice: Direct API calls with kubeconfig (stored as Kubernetes Secret)

    Rationale: Simple, standard, no additional infrastructure. The kubeconfig is written to a temp file per reconcile and cleaned up after. The namespace-scoped SA limits blast radius.

    CRD API Group¶

    Choice: hci-integration.openshift.io

    Used for WorkerPool, WorkerPoolProvisioning, and all future CRDs in this project.

    Implementation Phases¶

    Phase 1 — Steady-State Core ✅ COMPLETE¶

    Delivered: - WorkerPool CRD with CEL admission validation - Observe/diff/act reconcile loop - Scale-up and scale-down with set-difference logic (gap-fill correct) - ScaleDownBlocked + CountExceedsMaxPoolSize + ProviderCredentialsReady conditions - Status counts: deployedWorkers, readyWorkers, pendingWorkers - Phase sub-states: ScalingUp, ScalingDown, ScalingDownBlocked, Ready, Deprovisioned - Drain gate: cordon + no non-system pods before VM deletion - Local-storage node protection via annotation - Finalizer/cleanup role with workload-safety gate - Minimal RBAC ServiceAccount - Bastion-based dev workflow with run-local.sh

    Confirmed e2e on a live test cluster pair: full lifecycle (create → scale-up → scale-down → delete) verified including status counts and phase transitions.

    Phase 2 — Bootstrap Operator (Epic 2) ✅ LARGELY COMPLETE¶

    Delivered: - WorkerPoolProvisioning CRD with step-based state machine (wpp) - WorkerPool CRD split into spec.provider + spec.consumer (BS-00b refactor) - UDN step: create/delete UserDefinedNetwork router-internal-network on HCI (BS-03) - Gateway VM step: full cloud-init stack (DHCP, PXE/iPXE, nginx, ignition, RHCOS sync) (BS-04) - Ignition step: generate worker-hci.ign, SCP to gateway nginx root (BS-06a) - Bootfiles version gate: desired-version.txt drift detection, scale-up gate (BS-06b) - MachineConfig step: validate MachineConfigPool exists and is healthy (BS-02) - Workers teardown step: delete all consumer VMs before UDN teardown (BS-08) - Single credential secret (hci-provisioner-credentials) via setup-provider-credentials.sh - BS-05 deliberately descoped: manual script remains the documented handover tool

    Confirmed e2e: apply one WorkerPool CR → gateway provisions → workers PXE-boot and join cluster → scale up/down → delete CR → full teardown. See CURRENT-STATUS.md.

    Remaining: - [ ] BS-02b: Parameterised MachineConfig setup script for LinuxONE admin - [ ] BS-07: Optional image registry mirror (ImageContentSourcePolicy)

    Phase 3 — HCI Provider Operator (Epic 3)¶

    Goal: Remove the last manual step — HCI admin no longer needs to run scripts.

    Deliverables: - [ ] HCI-01: ComputeConsumerRequest + ComputeConsumerOrder CRDs on HCI - [ ] HCI-02: HCI Provider Operator scaffold + watches - [ ] HCI-03: Process Order: namespace + CUDN label + ResourceQuota - [ ] HCI-04: Generate onboarding ticket (privileged bootstrap SA + time-limited token) - [ ] HCI-05: Quota enforcement and usage monitoring

    Phase 4 — Negotiation Flow (Epic 4, Deferred)¶

    Goal: LO-initiated requests — no out-of-band communication needed.

    Design open. Requires a solution to the bootstrap discovery problem before stories can start. Deferred to iteration 2.

    Contributing¶

    Development Setup (Bastion-Based)¶

    # On the cluster bastion
git clone https://github.com/IBM/fusion-hci-integration
cd fusion-hci-integration

python3.11 -m venv --system-site-packages ~/ansible-operator-venv
source ~/ansible-operator-venv/bin/activate
pip install ansible-runner kubernetes openshift
ansible-galaxy collection install kubernetes.core redhat.openshift operator_sdk.util

# Consumer operator
cd operator/hci-consumer
./run-local.sh          # normal reconcile
./run-local.sh --cleanup  # simulate CR deletion

# Provisioner operator
cd operator/hci-provisioner
./run-local.sh          # normal reconcile
./run-local.sh --cleanup  # simulate CR deletion

    See operator/hci-consumer/README.md for the full development guide.

    Code Standards¶

    • Ansible tasks: one logical step per task, descriptive name: field
    • All API calls in observe_world.yml — zero API calls in diff or act files
    • Conditions set/cleared symmetrically — every True has a paired False path
    • Use set_fact for computed values; never compute inline in when: guards
    • YAML strings: avoid backslash in >- blocks (use character classes like ([.]|$))
