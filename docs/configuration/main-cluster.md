# Main Cluster Configuration

This document describes the main-cluster side of the integration: what has to exist on the main OpenShift cluster (and its bastion) so that x86 worker VMs hosted on the HCI cluster can join it.

!!! info "Manual steps behind the scripted setup"
    You normally do **not** perform these steps by hand. The
    [Setup Guide – Tier C](../getting-started.md#tier-c-connect-a-main-cluster)
    runs them for you with scripts, using the values from your
    `integration-setup.yaml` (rendered into `setup_env.sh` and `workspace/` by
    `generate-setup`). This page documents what each step does, so you can
    understand, verify, or repeat a single step manually.

    | Manual step on this page | Setup Guide step | Done by |
    |---|---|---|
    | [Bastion routing and firewall](#bastion-routing-and-firewall-mediated-topology-only) | [C.2](../getting-started.md#c2-configure-bastion-routing-and-firewall-mediated-topology-only) | `main-cluster/scripts/01-add-route.sh`, `02-firewall-setup.sh` |
    | [MachineConfigPool and MachineConfigs](#machineconfigpool-and-machineconfigs) | [C.4](../getting-started.md#c4-apply-machineconfigs) | `oc apply -k` on the overlay (or the `hci-consumer` operator) |
    | [Registry proxy](#registry-configuration-cross-cluster-model-only) | [C.5](../getting-started.md#c5-configure-bastion-registry-proxy), [C.6](../getting-started.md#c6-create-the-registry-access-secret) | `main-cluster/bastion-registry/setup-registry-proxy.sh`, `setup-registry-access.sh` |
    | [HCI Node Manager](#hci-node-manager) | [C.8](../getting-started.md#c8-build-and-deploy-the-operators) | Deployed with the `hci-consumer` operator |
    | Operator credentials, WorkerPool CR | [C.7](../getting-started.md#c7-create-operator-credentials), [C.9](../getting-started.md#c9-apply-the-workerpool-cr) | See [HCI Cluster Configuration](hci-cluster.md) |

    DNS ([C.1](../getting-started.md#c1-configure-dns-on-the-bastion)) and multi-architecture
    support ([C.3](../getting-started.md#c3-enable-multi-architecture-support)) are
    covered only in the Setup Guide.

## Overview

The main-cluster configuration consists of:

1. **MachineConfigPool and MachineConfigs** — created automatically by the `hci-consumer` operator from the `WorkerPool` CR; kustomize overlays exist as an optional manual fallback
2. **Deployment variant** — the *mediated* or *direct* overlay (the direct overlay adds static routes)
3. **Bastion routing** — mediated topology only
4. **Registry configuration** — only when `registry.model: cross-cluster`

## Prerequisites

Before configuring the main cluster, ensure:

- ✅ Main cluster is operational (OpenShift 4.20+)
- ✅ Cluster admin access available (`${MAIN_CLUSTER_CONTEXT}`)
- ✅ Network connectivity to the HCI cluster established
- ✅ `integration-setup.yaml` written and `generate-setup` run (see [Workspace Setup](../getting-started.md#workspace-setup))
- ✅ Topology (`mediated` or `direct`) and registry model chosen in `integration-setup.yaml`

See [Prerequisites](../prerequisites.md) for detailed requirements.

## Configuration Components

### Directory Structure

```
main-cluster/
├── configuration/
│   ├── base/                    # Common configuration
│   │   ├── kustomization.yaml
│   │   ├── machineconfig-pool-hci-vm.yaml
│   │   └── machineconfig-hci-vm-kargs.yaml
│   └── overlays/
│       ├── mediated/            # Mediated topology (no extra resources)
│       │   ├── kustomization.yaml
│       │   └── README.md
│       └── direct/              # Direct topology (adds route MachineConfigs)
│           ├── kustomization.yaml
│           ├── 99-master-s390x-hci-network-route.yaml   # generated
│           ├── 99-worker-s390x-hci-network-route.yaml   # generated
│           └── README.md
├── scripts/                     # Bastion helper scripts
└── bastion-registry/            # Registry proxy (cross-cluster model)
```

!!! info "MachineConfigs are operator-managed"
    The `hci-consumer` operator creates the `MachineConfigPool`, the kernel-argument
    `MachineConfig` and — for the direct topology — the two route `MachineConfigs`
    from the `WorkerPool` CR if they do not exist. The kustomize overlays are
    the equivalent manual path: apply them if you want the pool to exist before the
    operator first reconciles (Setup Guide step C.4 does exactly that).

!!! note "Generated route MachineConfigs"
    The two `99-*-s390x-hci-network-route.yaml` files in `overlays/direct/` are
    **generated by `generate-setup`** from `provider.networking.internalSubnet`
    and `provider.gateway.ip`. They are only written for `topology: direct`. Do
    not edit them by hand — change `integration-setup.yaml` and re-run
    `generate-setup`.

## Bastion Routing and Firewall (Mediated Topology only)

**Setup Guide:** [C.2](../getting-started.md#c2-configure-bastion-routing-and-firewall-mediated-topology-only)

In the mediated topology the main-cluster nodes reach the HCI worker subnet
through the bastion. The bastion needs a route to the internal subnet via the
gateway VM's external IP, and a firewall rule that admits the internal subnet:

```bash
# Route: 192.168.100.0/24 via 172.16.1.100 (gateway external IP)
sudo ./main-cluster/scripts/01-add-route.sh
sudo ./main-cluster/scripts/02-firewall-setup.sh

ip route show | grep 192.168.100.0/24
# 192.168.100.0/24 via 172.16.1.100
```

The scripts source the generated `setup_env.sh` from the repository root
(`INTERNAL_NETWORK`, `ROUTER_VM_EXTERNAL`).

## MachineConfigPool and MachineConfigs

**Setup Guide:** [C.4](../getting-started.md#c4-apply-machineconfigs)

### Step 1: Review the Base MachineConfigs

#### MachineConfigPool

**File:** `base/machineconfig-pool-hci-vm.yaml`

**Purpose:** Create a separate pool for the HCI workers

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: hci-vm
  labels:
    machineconfiguration.openshift.io/role: hci-vm
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - hci-vm
    - key: node-platform
      operator: NotIn
      values:
      - s390x
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/hci-vm: ""
  paused: false
  maxUnavailable: 1
```

**Key Features:**

- Separate from the main worker pool; the name is `consumer.machineConfigPool` (default `hci-vm`)
- Selects nodes with the `node-role.kubernetes.io/hci-vm: ""` label
- Excludes MachineConfigs labelled `node-platform: s390x`, so the s390x route MachineConfig never lands on x86 VMs
- Can be paused independently for maintenance

#### Kernel Arguments

**File:** `base/machineconfig-hci-vm-kargs.yaml` (`99-hci-vm-kargs`; also created by the operator on first reconcile if absent)

**Purpose:** Configure HCI worker-specific boot settings

```yaml
kernelArguments:
  - "root=/dev/disk/by-label/root"
  - "rd.multipath=0"    # Disable multipath — not needed for VMs
  - "rd.neednet=1"
  - "ip=enp1s0:off"     # Disable the HCI pod-network interface (prevents OVN conflicts)
  - "ip=enp2s0:dhcp"    # Cluster network interface via (static-lease) DHCP
```

Node role labeling is done automatically by the `node-labeler` sidecar in the
`hci-consumer-operator` pod — no MachineConfig labeling is required.

### Step 2: Choose the Deployment Variant

The variant follows `consumer.networking.topology` in `integration-setup.yaml`.

#### Mediated Topology (Private Network)

**When to use:**

- Main-cluster nodes sit on a private network (example: `10.0.0.0/24`)
- The bastion (`172.16.0.1` in the example) routes all traffic to the HCI gateway
- Common in z/VM and LPAR environments

**What's included:** the base MachineConfigPool and kernel arguments. No additional
routing on the cluster nodes — the bastion handles it.

**Apply:**
```bash
oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/mediated/
```

#### Direct Topology (Public Network)

**When to use:**

- Main-cluster nodes are on the same routable network as the HCI gateway's external IP (`172.16.1.100` in the example)
- Common in KVM and bare-metal environments

**What's included:** the base resources plus one static-route MachineConfig for
the master nodes and one for the s390x worker nodes, each routing the internal
subnet (`192.168.100.0/24`) via the gateway's external IP.

**Apply:**
```bash
oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/direct/
```

See [Deployment Variants](../deployment-variants.md) for a detailed comparison.

## Applying Configuration

### Step 1: Apply Base + Overlay

**For Mediated Topology:**
```bash
cd /path/to/fusion-hci-integration

oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/mediated/

# Verify the MachineConfigPool
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm

# Expected output:
# NAME     CONFIG    UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT
# hci-vm   rendered  True      False      False      0              0
```

**For Direct Topology:**
```bash
oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/direct/

oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-master-s390x-hci-network-route
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-worker-s390x-hci-network-route

# The master and worker pools roll out the new route
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp master worker
```

### Step 2: Wait for MachineConfig Application

**Mediated Topology:** no node updates are required; the pool is ready immediately.

**Direct Topology:** master nodes and s390x worker nodes restart one by one. This
can take 10–30 minutes.

```bash
watch oc --context ${MAIN_CLUSTER_CONTEXT} get mcp master worker

# Wait for UPDATED=True, UPDATING=False, DEGRADED=False
```

### Step 3: Verify Configuration

```bash
# Pool details
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm -o yaml
# - machineConfigSelector includes "hci-vm"
# - nodeSelector matches node-role.kubernetes.io/hci-vm: ""
# - paused: false

# MachineConfigs for the HCI pool
oc --context ${MAIN_CLUSTER_CONTEXT} get mc | grep -E "hci"
# 99-hci-vm-kargs
# 99-master-s390x-hci-network-route   (direct topology only)
# 99-worker-s390x-hci-network-route   (direct topology only)
```

**Direct topology — verify the routes on a node:**
```bash
oc --context ${MAIN_CLUSTER_CONTEXT} debug node/<master-node>
chroot /host
ip route | grep 192.168.100
# 192.168.100.0/24 via 172.16.1.100 dev br-ex

# Same check on an s390x worker (no "dev br-ex")
# 192.168.100.0/24 via 172.16.1.100
```

## HCI Node Manager

**Setup Guide:** [C.8](../getting-started.md#c8-build-and-deploy-the-operators) (deployed with the operator)

### Purpose

Automates the HCI worker node lifecycle:

- **CSR approval** — approves the bootstrap and serving CSRs of the worker VMs
- **Node labeling** — applies `node-role.kubernetes.io/hci-vm: ""`

### Deployment

The node manager runs as two sidecar containers (`csr-approver` and `node-labeler`)
inside the `hci-consumer-operator` Deployment. It is deployed automatically as part of
the operator — no separate build or deployment step is required.

The sidecars are configured via the `hci-node-manager-config` ConfigMap, which the
operator writes on every reconcile from the `WorkerPool` CR:

| ConfigMap key | Source |
|---|---|
| `NODE_NAME_PATTERN` | `spec.consumer.workers.namePrefix` (example: `worker-x86`) |
| `TARGET_NETWORK` | `spec.provider.networking.internalSubnet` (example: `192.168.100.0/24`) |

The cluster domain is derived automatically from `config.openshift.io/v1 DNS/cluster`
— no manual configuration is needed.

Both sidecars re-read the ConfigMap every ~30 s, so a pod that started before the
first reconcile picks up the config by itself. The `node-labeler` labels a node only
if its name matches `<NODE_NAME_PATTERN>-<N>`, its `kubernetes.io/arch` is `amd64`,
**and** its InternalIP is in `TARGET_NETWORK`. This keeps s390x control-plane and
compute nodes out of the `hci-vm` MachineConfigPool even if the networks overlap.

### Verification

```bash
# The consumer operator pod (the sidecars are containers within it)
oc --context ${MAIN_CLUSTER_CONTEXT} get pods -n hci-node-manager \
  -l app.kubernetes.io/name=hci-consumer-operator

# csr-approver logs
oc --context ${MAIN_CLUSTER_CONTEXT} logs -n hci-node-manager \
  deploy/hci-consumer-operator -c csr-approver | tail -20

# node-labeler logs
oc --context ${MAIN_CLUSTER_CONTEXT} logs -n hci-node-manager \
  deploy/hci-consumer-operator -c node-labeler | tail -20
```

## Registry Configuration (Cross-Cluster Model only)

**Setup Guide:** [C.5](../getting-started.md#c5-configure-bastion-registry-proxy) and [C.6](../getting-started.md#c6-create-the-registry-access-secret)

### When Needed

Only when `registry.model: cross-cluster` is set in `integration-setup.yaml`. With
`local-s2i` or `external`, skip this section.

### Setup

**Location:** `main-cluster/bastion-registry/`

1. **Bastion HAProxy and cluster insecure-registry entry** — run as your normal user,
   **not** with `sudo` (the script uses `sudo` internally for HAProxy, firewall and
   certificates, and runs `oc` with your own login against `${MAIN_CLUSTER_CONTEXT}`):

    ```bash
    ./main-cluster/bastion-registry/setup-registry-proxy.sh
    ```

    The script generates a self-signed certificate, configures HAProxy to forward
    `bastion.cluster.example.com:5443` to the HCI registry, and adds that address to
    `image.config.openshift.io/cluster` `spec.registrySources.insecureRegistries`
    on the main cluster. That change triggers a MachineConfigPool rollout (10–30
    minutes).

2. **Registry push secret** — reads the token of the `registry-pusher` ServiceAccount
   from the HCI cluster (created by `setup-consumer-rbac.sh`, see
   [HCI Cluster Configuration](hci-cluster.md#step-3-rbac-for-the-operators)) and
   stores it as a docker-registry Secret on the main cluster:

    ```bash
    ./main-cluster/bastion-registry/setup-registry-access.sh
    # creates Secret hci-registry-push in namespace hci-node-manager
    ```

Verify:

```bash
oc --context ${MAIN_CLUSTER_CONTEXT} get image.config.openshift.io cluster \
  -o jsonpath='{.spec.registrySources.insecureRegistries}'
curl -sk https://localhost:5443/v2/ && echo ok     # on the bastion
oc --context ${MAIN_CLUSTER_CONTEXT} get secret hci-registry-push -n hci-node-manager
```

See the [Bastion Registry README](https://github.com/IBM/fusion-hci-integration/tree/main/main-cluster/bastion-registry/README.md) for details.

## Post-Configuration Tasks

### Step 1: Verify the MachineConfigPool

```bash
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm

# MACHINECOUNT: 0 (no workers yet)
# READYMACHINECOUNT: 0
# UPDATED: True   UPDATING: False   DEGRADED: False
```

### Step 2: Prepare for Worker Join

CSRs are approved automatically by the `csr-approver` sidecar in the
`hci-consumer-operator` pod. No manual action is needed once the operator is deployed.

```bash
# Monitor csr-approver activity
oc --context ${MAIN_CLUSTER_CONTEXT} logs -n hci-node-manager \
  deploy/hci-consumer-operator -c csr-approver -f

# Manual approval (e.g. operator not yet deployed)
oc --context ${MAIN_CLUSTER_CONTEXT} get csr | grep Pending
oc --context ${MAIN_CLUSTER_CONTEXT} get csr | awk '/Pending/ {print $1}' \
  | xargs -r oc --context ${MAIN_CLUSTER_CONTEXT} adm certificate approve
```

### Step 3: Monitor Worker Join

```bash
watch oc --context ${MAIN_CLUSTER_CONTEXT} get nodes -l node-role.kubernetes.io/hci-vm
watch oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm

# As workers join, MACHINECOUNT and READYMACHINECOUNT increase
```

## Updating Configuration

### Updating MachineConfigs

```bash
# Edit the MachineConfig
vi main-cluster/configuration/base/machineconfig-hci-vm-kargs.yaml

# Apply the change
oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/<variant>/

# Workers restart to apply it
watch oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm
```

The `hci-consumer` operator only creates the MachineConfigs when they are absent; it
never overwrites an existing one, so manual changes are preserved.

**Pausing updates:**
```bash
oc --context ${MAIN_CLUSTER_CONTEXT} patch mcp hci-vm --type=merge -p '{"spec":{"paused":true}}'
# Make changes ...
oc --context ${MAIN_CLUSTER_CONTEXT} patch mcp hci-vm --type=merge -p '{"spec":{"paused":false}}'
```

### Switching Variants

**Not recommended:** switching the topology after deployment requires redeploying the workers.

**If necessary:**
```bash
# 1. Scale the pool to 0 workers (edit spec.consumer.workers.count) and wait
oc --context ${MAIN_CLUSTER_CONTEXT} -n hci-node-manager edit workerpool hci-workers

# 2. Delete the old route MachineConfigs (and the pool, if it is to be recreated)
oc --context ${MAIN_CLUSTER_CONTEXT} delete mc 99-master-s390x-hci-network-route 99-worker-s390x-hci-network-route --ignore-not-found

# 3. Change consumer.networking.topology in integration-setup.yaml,
#    re-run generate-setup, then apply the matching overlay
oc --context ${MAIN_CLUSTER_CONTEXT} apply -k main-cluster/configuration/overlays/<new-variant>/

# 4. Scale the pool back up
```

## Troubleshooting

### MachineConfigPool Stuck Updating

**Symptoms:** `UPDATING: True` for an extended period, or `DEGRADED: True`.

```bash
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm -o yaml
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp hci-vm -o jsonpath='{.status.conditions[*].message}'

# machine-config-daemon logs on affected nodes
oc --context ${MAIN_CLUSTER_CONTEXT} logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon
```

### Workers Not Joining the Pool

**Symptoms:** workers appear in the cluster but not in the `hci-vm` pool.

```bash
oc --context ${MAIN_CLUSTER_CONTEXT} get node worker-x86-1 --show-labels
# Should have: node-role.kubernetes.io/hci-vm

# The node-labeler requires: name matches worker-x86-<N>, arch amd64,
# InternalIP in 192.168.100.0/24.  Check its log first:
oc --context ${MAIN_CLUSTER_CONTEXT} logs -n hci-node-manager \
  deploy/hci-consumer-operator -c node-labeler | tail -30

# If you must label manually:
oc --context ${MAIN_CLUSTER_CONTEXT} label node worker-x86-1 node-role.kubernetes.io/hci-vm=
```

### CSRs Not Being Approved

```bash
oc --context ${MAIN_CLUSTER_CONTEXT} get csr | grep Pending

oc --context ${MAIN_CLUSTER_CONTEXT} logs -n hci-node-manager \
  deploy/hci-consumer-operator -c csr-approver | tail -30
```

### Routes Not Applied (Direct Topology)

```bash
# MachineConfigs exist
oc --context ${MAIN_CLUSTER_CONTEXT} get mc 99-master-s390x-hci-network-route 99-worker-s390x-hci-network-route

# Applied to the pools
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp master -o yaml | grep 99-master-s390x-hci-network-route
oc --context ${MAIN_CLUSTER_CONTEXT} get mcp worker -o yaml | grep 99-worker-s390x-hci-network-route

# Route on a node
oc --context ${MAIN_CLUSTER_CONTEXT} debug node/<node>
chroot /host
ip route | grep 192.168.100
```

See the [Troubleshooting Guide](../operations/troubleshooting.md) for detailed solutions.

## Best Practices

### Configuration Management

1. **Keep `integration-setup.yaml` as the single source of truth** — regenerate rather than hand-edit generated files
2. **Version control** — keep `integration-setup.yaml` and any customized MachineConfigs in Git (never the generated `setup_env.sh`/credentials)
3. **Test changes** — verify in a dev environment before production
4. **Document customizations** — maintain a changelog

### MachineConfigPool Management

1. **Separate pools** — keep HCI workers isolated
2. **Pause for maintenance** — prevent automatic updates during changes
3. **Monitor status** — watch for degraded state
4. **Plan updates** — schedule during maintenance windows

### Security

1. **Limit access** — use RBAC for MachineConfig management
2. **Audit changes** — review MachineConfig modifications
3. **Protect credentials** — secure ignition files, SSH keys and operator credential Secrets
4. **Regular updates** — keep RHCOS updated

### Operations

1. **CSR approval is automatic** — handled by the `csr-approver` sidecar in the consumer operator
2. **Monitor continuously** — set up alerts for pool status
3. **Test recovery** — verify disaster recovery procedures
4. **Document procedures** — maintain runbooks
