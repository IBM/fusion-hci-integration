# VM Provisioning Architecture

This document describes how worker VMs are provisioned, configured, and integrated into the main OpenShift cluster.

All names, addresses and sizes are the example values from
`templates/integration-setup.example.yaml`. The real values are set once in
`integration-setup.yaml`; see the field mapping in
[Architecture Overview](architecture-overview.md#configuration-input).

The resources and commands shown below describe what the operators create and what
you can inspect when troubleshooting. They are not manual deployment steps: the
`hci-provisioner` bootstraps the gateway VM and the ignition file, and the
`hci-consumer` creates the worker VMs, once `integration-setup.yaml` has been turned
into a `WorkerPool` by `generate-setup`.

## Overview

The VM provisioning process involves:

1. **VM Creation** - OpenShift Virtualization creates VMs on HCI cluster
2. **Network Boot** - VMs boot via iPXE from the gateway VM
3. **OS Installation** - RHCOS installs from ignition configuration
4. **Cluster Join** - Workers register with main cluster
5. **Configuration** - MachineConfig applies worker-specific settings

## Provisioning Components

### 1. OpenShift Virtualization (KubeVirt)

**Purpose:** Provides VM infrastructure on HCI cluster

**Key Resources:**
- `VirtualMachine` - VM definition and lifecycle
- `VirtualMachineInstance` - Running VM instance
- `DataVolume` - VM disk storage
- `UserDefinedNetwork` - Network connectivity (`router-internal-network`)

**VM definition created by the `hci-consumer` (abridged):**
```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: worker-x86-1
  namespace: main-cluster-workers
spec:
  running: true
  template:
    metadata:
      annotations:
        k8s.v1.cni.cncf.io/networks: '[{"name":"router-internal-network","interface":"internal"}]'
    spec:
      domain:
        cpu:
          cores: 4
        resources:
          requests:
            memory: 8Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
            bootOrder: 2
          interfaces:
          - name: default            # pod network, not used for cluster traffic
            masquerade: {}
            bootOrder: 3
          - name: internal           # worker network, boots first
            bridge: {}
            bootOrder: 1
            macAddress: "52:54:01:00:00:10"
      networks:
      - name: default
        pod: {}
      - name: internal
        multus:
          networkName: router-internal-network
      volumes:
      - name: rootdisk
        dataVolume:
          name: worker-x86-1-rootdisk
```

### 2. Gateway VM

**Purpose:** Provides provisioning services

**Services:**
- **DHCP** - IP address assignment
- **TFTP** - Boot file serving
- **HTTP** - Ignition config serving
- **DNS** - Name resolution

**Configuration:** created by the `hci-provisioner` (GatewayVM step) from a
cloud-init template filled with the `provider.gateway.*`, `provider.networking.*` and
`consumer.networking.*` values of `integration-setup.yaml`. `dnsmasq` provides
DHCP, TFTP and DNS; `nginx` serves the ignition file. Nothing is installed or enabled
by hand.

### 3. Ignition Configuration

**Purpose:** Configures RHCOS during first boot

**Source:** Generated by the `hci-provisioner` (Ignition step) from the
`worker-user-data-managed` Secret in `openshift-machine-api` on the main cluster.
The result is a small stub that points the worker at the Machine Config Server of
the configured MachineConfigPool (`consumer.machineConfigPool`, example `hci-vm`),
and is copied to the gateway VM's HTTP server. It does not depend on the OpenShift
version and is created once at bootstrap.

The worker hostname is not part of the ignition file. It is handed out by the
gateway's DHCP server per worker slot (`<namePrefix>-<index>.<domain>`).

## Provisioning Flow

### Phase 1: VM Creation

```
WorkerPool CR (hci-consumer operator)
        ↓
hci-consumer: observe/diff/act reconcile
        ↓
Create VirtualMachine Resource on HCI
        ↓
Allocate Storage (DataVolume)
        ↓
Attach Networks (NADs from WorkerPoolProvisioning)
        ↓
Start VM (VirtualMachineInstance)
```

**WorkerPool CR spec (excerpt):**
```yaml
spec:
  consumer:
    workers:
      count: 3
      namePrefix: worker-x86
  provider:
    namespace: main-cluster-workers
    maxPoolSize: 10
```

### Phase 2: Network Boot (iPXE)

The gateway VM runs `dnsmasq` (DHCP and TFTP) and `nginx` (HTTP). The worker VM
boots from its internal NIC first (`bootOrder: 1`), so the sequence below starts as
soon as it is powered on.

```
VM Powers On
        ↓
PXE firmware requests DHCP on the internal network
        ↓
Gateway VM answers from its static reservation for this MAC
  - IP:        192.168.100.10   (fixed per worker slot)
  - Hostname:  worker-x86-1.cluster.example.com
  - Gateway:   192.168.100.1
  - DNS:       172.16.0.1       (consumer.networking.dnsServer)
  - Boot file: undionly.kpxe    (served via TFTP)
        ↓
Firmware downloads undionly.kpxe via TFTP and starts iPXE
        ↓
iPXE requests DHCP again (it announces itself with DHCP option 175)
        ↓
Gateway VM answers with an HTTP boot URL instead
  - http://192.168.100.1/boot.ipxe
        ↓
iPXE runs boot.ipxe: 10-second menu, default "Boot from local disk"
  - disk empty or not bootable → falls through to "Install RHCOS"
        ↓
iPXE loads the RHCOS live kernel and initramfs over HTTP
```

**DHCP:** the gateway does not hand out addresses from a dynamic range. It runs
`dnsmasq` in static-only mode (`dhcp-range=192.168.100.0,static`) with one
`dhcp-host` entry for every possible worker slot, up to `provider.maxPoolSize`.
Each entry fixes MAC address, IP address and hostname (see
[MAC Address Assignment](#mac-address-assignment)). Scaling workers up or down
within the pool limit therefore never requires a gateway change.

**Boot parameters (from `boot.ipxe`):**
```
kernel http://192.168.100.1/rhcos/rhcos-live-kernel \
  ip=enp2s0:dhcp ip=enp1s0:off rd.neednet=1 \
  coreos.inst.install_dev=/dev/vda \
  coreos.live.rootfs_url=http://192.168.100.1/rhcos/rhcos-live-rootfs.img \
  coreos.inst.ignition_url=http://192.168.100.1/rhcos/worker-hci.ign \
  ignition.platform.id=metal \
  coreos.inst.node-role.kubernetes.io/hci-vm= \
  coreos.inst.karg=rd.multipath=0 ...
initrd http://192.168.100.1/rhcos/rhcos-live-initramfs.img
```

`enp2s0` is the internal NIC (DHCP), `enp1s0` the pod-network NIC (left unconfigured).

**Boot files:** the kernel, initramfs and rootfs under `/rhcos/` are downloaded by
the gateway itself from the OpenShift mirror (`rhcos-sync.timer`, every 5 minutes),
for the RHCOS stream requested by the operator. Scale-up is held back until the
download is complete.

### Phase 3: OS Installation

```
RHCOS live image boots (kernel + initramfs + rootfs over HTTP)
        ↓
Fetch Ignition Config
  URL: http://192.168.100.1/rhcos/worker-hci.ign
        ↓
coreos-installer writes RHCOS to /dev/vda
        ↓
Reboot from disk
        ↓
Ignition stub on first boot contacts the Machine Config Server
  - https://api-int.cluster.example.com:22623/config/hci-vm
  - outbound traffic is routed (and NATed where needed) by the gateway VM
```

The ignition file is the stub described in
[Ignition Configuration](#3-ignition-configuration); the actual machine configuration
is pulled from the main cluster's Machine Config Server for the `hci-vm` pool.

**Installation Progress:**
```bash
# Monitor from VM console
journalctl -u coreos-installer -f
```

### Phase 4: First Boot

```
VM Boots from Disk
        ↓
Ignition stub runs (first boot)
  - contacts the Machine Config Server of the main cluster
  - https://api-int.cluster.example.com:22623/config/hci-vm
  - merges the rendered configuration of the hci-vm pool
        ↓
Start kubelet (with the bootstrap credentials from that configuration)
        ↓
Kubelet submits a bootstrap CSR (client certificate) to the main cluster
```

**Boot Process:**
```bash
# Key services
systemctl status kubelet
systemctl status crio
```

### Phase 5: Cluster Join

Two CSRs are involved. Both are approved automatically by the `csr-approver` sidecar of
the `hci-consumer-operator` pod, and only for node names that match the worker name
prefix (`consumer.workers.namePrefix`).

```
Bootstrap CSR (client certificate)
  - approved by csr-approver while the node object does not exist yet
        ↓
Node object registers in the main cluster
        ↓
Kubelet submits a serving CSR (server certificate)
  - approved by csr-approver once the node object exists
        ↓
Node Labeled by node-labeler
  - node-role.kubernetes.io/hci-vm: ""
  - only if: arch amd64, InternalIP in the internal subnet, name matches prefix
        ↓
Node matches the MachineConfigPool nodeSelector (pool: hci-vm)
        ↓
machine-config-daemon applies the pool's MachineConfigs
        ↓
Node Ready
```

Manual fallback if a CSR stays pending: `oc adm certificate approve <csr>`.

**Verification:**
```bash
# Check CSRs
oc get csr | grep Pending

# Check nodes
oc get nodes -l node-role.kubernetes.io/hci-vm

# Check MachineConfigPool
oc get mcp hci-vm
```

## Storage Provisioning

### DataVolume Creation

**Purpose:** Provides persistent storage for VM

**Configuration:**
```yaml
apiVersion: cdi.kubevirt.io/v1beta1
kind: DataVolume
metadata:
  name: worker-x86-1-rootdisk
spec:
  pvc:
    accessModes:
    - ReadWriteOnce
    resources:
      requests:
        storage: 50Gi            # consumer.workers.resources.storage
    storageClassName: ocs-storagecluster-ceph-rbd-virtualization
    volumeMode: Block
  source:
    blank: {}
```

The disk is created blank; RHCOS is written to it by the installer during
[Phase 3](#phase-3-os-installation).

**Storage class:** `ocs-storagecluster-ceph-rbd-virtualization` (Ceph RBD block
storage optimised for virtualization) is used for all worker disks.

### Disk Layout

The installer writes the standard RHCOS layout to the virtual disk (`/dev/vda`,
50Gi by default). The operators do not define a custom partitioning.

### Storage Performance

**Considerations:**
- **IOPS** - Ceph RBD provides good random I/O
- **Throughput** - Network-attached storage limits
- **Latency** - Typically 1-5ms for Ceph
- **Capacity** - Plan for OS + container images + logs

## Network Provisioning

### Network Attachment

Worker VMs attach to the `router-internal-network` `UserDefinedNetwork` that the
`hci-provisioner` creates in `provider.namespace` (see
[Network Design](network-design.md#2-layer2-internal-network)). OVN-Kubernetes
generates the matching `NetworkAttachmentDefinition` from it; none is written by hand.
Each VM references it in a Multus annotation and a `multus` network.

**IP Configuration:**
- **DHCP** - From the gateway VM, using a static per-slot reservation (MAC → IP → hostname)

### MAC Address Assignment

**Fixed MAC Addresses:**

MACs are derived as `<macPrefix>:00:00:<hex>` with `hex = 0x10 + (index - 1)`.
`macPrefix` is `provider.networking.macPrefix` from `integration-setup.yaml`
(example: `52:54:01`), so `worker-x86-1` gets:

```yaml
interfaces:
- name: internal
  macAddress: "52:54:01:00:00:10"
  bridge: {}
```

**Why Fixed MACs?**
- The gateway's static DHCP reservations are keyed on the MAC
- Predictable IP address and hostname per worker slot
- Easier troubleshooting

## Configuration Management

### MachineConfig Application

**Timeline** (starts when the node has been labeled, see [Platform Labeling](#platform-labeling)):
```
Node Labeled (t=0)
        ↓
Node matches the MachineConfigPool nodeSelector (t=0)
        ↓
machine-config-daemon takes over the node (t=0)
        ↓
Check rendered MachineConfig of the pool (t=0-30s)
        ↓
Apply Configuration (t=30s-2m)
  - Kernel arguments
  - System files
  - Systemd units
        ↓
Reboot if Required (t=2m)
        ↓
Verify Configuration (t=3m)
        ↓
Node Ready (t=3-5m)
```

### MachineConfigPool

**Purpose:** Group workers with common configuration

The pool name comes from `consumer.machineConfigPool` (default and example: `hci-vm`).
If the pool and its kernel-argument MachineConfig (`99-hci-vm-kargs`) do not exist,
the `hci-consumer` creates them; existing ones are never modified.

```yaml
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: hci-vm
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - hci-vm
    - key: node-platform
      operator: NotIn
      values:
      - s390x
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/hci-vm: ""
  paused: false
  maxUnavailable: 1
```

**Key Features:**
- Separate from main worker pool
- Can pause updates independently
- Allows HCI-specific configuration

### Platform Labeling

**Automatic Labeling:** the `node-labeler` sidecar of the `hci-consumer` operator
adds `node-role.kubernetes.io/hci-vm: ""` to a new node only if all of these hold:

- the node's architecture is `amd64`
- its InternalIP is within the internal worker subnet (`provider.networking.internalSubnet`)
- its name matches the worker name pattern (`consumer.workers.namePrefix`)

The sidecar reads these values from the `hci-node-manager-config` ConfigMap, which the
operator writes from the `WorkerPool`. Nodes of other architectures are never labeled,
so the s390x nodes cannot be moved into the `hci-vm` pool by mistake.

**Why Automatic?**
- Ensures correct pool assignment
- Prevents configuration conflicts
- Simplifies operations

## Automation

### HCI Node Manager (sidecars)

**Purpose:** Automate node lifecycle tasks

**Functions:**
1. **CSR Auto-Approval** (`csr-approver`) — approves worker CSRs automatically via a Kubernetes watch stream
2. **Node Labeling** (`node-labeler`) — applies `node-role.kubernetes.io/hci-vm: ""` so the node joins the correct MachineConfigPool

**Deployment:** The node manager runs as two sidecar containers inside the `hci-consumer-operator`
Deployment. No standalone Deployment is required. Both sidecars read their config from the
`hci-node-manager-config` ConfigMap, which the operator writes on every `WorkerPool` reconcile.

```bash
# Check sidecars
oc get pods -n hci-node-manager -l app.kubernetes.io/name=hci-consumer-operator

# Logs
oc logs -n hci-node-manager deploy/hci-consumer-operator -c csr-approver | tail -20
oc logs -n hci-node-manager deploy/hci-consumer-operator -c node-labeler | tail -20
```

### Operator Automation

**Purpose:** Declarative, self-healing VM lifecycle management

**Features:**
- Observe/diff/act reconcile loop — continuously converges to desired state
- Safe scale-down: cordon + drain gate before VM deletion
- Status conditions and phase sub-states on the `WorkerPool` CR
- Bootstrap (gateway VM, UDN, ignition) managed by `hci-provisioner`

**Usage:** `generate-setup` creates the initial `WorkerPool` with `workers.count: 0`.
Scale by editing the live resource in the operator namespace
(`consumer.operatorNamespace`, example `hci-node-manager`):

```bash
# Scale up
oc -n hci-node-manager patch workerpool hci-workers \
  --type merge -p '{"spec":{"consumer":{"workers":{"count":4}}}}'

# Scale down
oc -n hci-node-manager patch workerpool hci-workers \
  --type merge -p '{"spec":{"consumer":{"workers":{"count":2}}}}'

# Watch status
oc -n hci-node-manager get workerpool hci-workers -w
```

Re-running `generate-setup` rewrites the `WorkerPool` file with `workers.count: 0`;
use `oc get workerpool hci-workers -o yaml` to keep the live state.

## Monitoring Provisioning

### Key Metrics

**VM Creation:**
- Time to create VM: Target <2 minutes
- Storage allocation time: Target <1 minute
- Network attachment time: Target <30 seconds

**Network Boot:**
- DHCP response time: Target <1 second
- TFTP download of `undionly.kpxe`: Target <30 seconds
- iPXE boot menu: 10 seconds, then installs automatically if the disk is empty

**OS Installation:**
- Ignition fetch time: Target <5 seconds
- RHCOS download time: Target 5-10 minutes
- Installation time: Target 10-15 minutes
- Total time: Target 15-20 minutes

**Cluster Join:**
- CSR generation: Target <1 minute
- CSR approval: Target <1 minute (auto) or manual
- Node registration: Target <2 minutes
- Node ready: Target <5 minutes

### Monitoring Commands

```bash
# Watch VM creation
watch oc get vm -n main-cluster-workers

# Monitor network boot (from VM console)
virtctl console -n main-cluster-workers worker-x86-1

# Check installation progress
oc logs -n main-cluster-workers virt-launcher-worker-x86-1-xxxxx

# Monitor cluster join
watch oc get csr
watch oc get nodes -l node-role.kubernetes.io/hci-vm

# Check MachineConfigPool
watch oc get mcp hci-vm
```

## Troubleshooting

### VM Won't Start

**Symptoms:**
- VM stuck in "Starting" state
- VirtualMachineInstance not created

**Checks:**
```bash
# Check VM events
oc describe vm worker-x86-1 -n main-cluster-workers

# Check DataVolume
oc get dv -n main-cluster-workers

# Check storage capacity
oc get pvc -n main-cluster-workers
```

### Network Boot Fails

**Symptoms:**
- VM shows "No bootable device"
- DHCP request times out
- iPXE starts but cannot load `boot.ipxe` or the RHCOS kernel

**Checks:**
```bash
# Check gateway VM (named hci-gateway)
oc get vmi hci-gateway -n main-cluster-workers

# Log in to the gateway (external IP = provider.gateway.ip)
ssh core@172.16.1.100

# On the gateway: DHCP/TFTP and HTTP services
sudo systemctl status dnsmasq nginx

# On the gateway: is the worker's MAC being offered an address?
sudo journalctl -u dnsmasq | grep -i dhcp | tail -20

# On the gateway: iPXE loader, boot script and RHCOS boot files
ls -la /var/lib/tftpboot/
ls -la /var/www/html/ /var/www/html/rhcos/
cat /var/www/html/rhcos/current-version.txt
```

If `current-version.txt` is missing, the gateway has not finished downloading the RHCOS
boot files yet (`systemctl status rhcos-sync.timer`, `journalctl -u rhcos-sync`).

### Installation Fails

**Symptoms:**
- Installation hangs
- Cannot fetch ignition
- Disk errors

**Checks:**
```bash
# Check ignition availability (from the gateway or any host on the internal network)
curl -I http://192.168.100.1/rhcos/worker-hci.ign

# Check disk
virtctl console -n main-cluster-workers worker-x86-1
# In console: lsblk, fdisk -l

# Check logs
journalctl -u coreos-installer
```

### Node Won't Join

**Symptoms:**
- CSR not generated
- CSR pending forever
- Node not appearing

**Checks:**
```bash
# Check CSRs
oc get csr | grep worker-x86

# Check kubelet
oc debug node/worker-x86-1
chroot /host
systemctl status kubelet
journalctl -u kubelet -n 100

# Check connectivity
ping api.cluster.example.com
curl -k https://api.cluster.example.com:6443/version
```

See [Troubleshooting Guide](../operations/troubleshooting.md) for detailed solutions.

## Best Practices

### VM Configuration

1. **Use fixed MAC addresses** - Ensures consistent networking
2. **Allocate sufficient resources** - defaults are 4 vCPU, 8GB RAM, 50GB disk (`consumer.workers.resources`); size to your workload
3. **Use block storage** - Better performance than file storage
4. **Enable virtio drivers** - Optimal performance

### Provisioning

1. **Test with one worker first** - Verify process works
2. **CSR approval is automatic** — the `csr-approver` sidecar in the operator handles it
3. **Monitor provisioning** - Watch for failures
4. **Document custom configurations** - Keep ignition changes tracked

### Operations

1. **Use operator CRs for management** - Declarative and version-controlled
2. **Keep gateway VM updated** - Security patches
3. **Backup configurations** - CR manifests, ignition configs
4. **Plan for failures** - Have recovery procedures ready
